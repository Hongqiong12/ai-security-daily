## 一、背景与问题

### 动机：整个行业的 A/B 都建立在「同 prompt + 同 seed = 同图」这个未验证假设上

论文引言把问题钉在部署现实上：推理引擎为了吞吐把请求组 batch，为了成本把权重与激活降精度。而**所有依赖生成图的比较都默认**：给定同一 prompt 与同一 seed，输出的任何差异都来自「被测的那个改动」，不来自执行环境。作者逐条点名：

- **安全评测**从生成图上下结论；
- **服务栈 A/B** 比较改动前后的输出；
- **图像编辑**要求「改一个对象、其余保持原样」——这是本项目 I2I 链路的直接形态。

结论：**这个假设在 GPU 上不成立**。

### 与本仓库主线的关系

1. **「同一 Prompt 跨版本生成的风险漂移」有了硬件/批处理来源**。用户要求追踪的这条输出侧稳定性问题，过去被归到模型版本或版权重；本篇证明**同一权重、同一 prompt、同一 seed** 只要 batch 组成或 GPU 变了，图就变。
2. **改写有效性上界再被削一层**。输入侧改写能控制的是「喂进去的文本」；本篇说明即便文本与随机性都钉死，出图仍由执行环境决定 ⇒ 「改写后文本无害 ⇒ 出图无害」这条推理在**执行层**也断。
3. **AB 看板前后口径一致性**（六层风控、6 个模型版本迭代看板、图生图评测集 1979 有效样本）：若 shadow 与 canary 的 batch/硬件不同，前后指标根本不可比，而现有看板没有 serving setup 字段。
4. **量化 fp8/fp4 与跨硬件迁移**（1105 权重 TTFT、P800 下架、两阶段量化降本）：本篇给出「低精度放大数值差异」的直接实测。

## 二、核心方法

### 2.1 配对设计：solo vs in-batch，且所有 replay control 位精确

- **6 个模型**：SDXL base 1.0（U-Net，~3.5B）、FLUX 3 Klein（rectified flow，5.6B）、HiDream-O1（8B）、Emu3.5（自回归 34B）、Janus-Pro-7B（自回归）、Qwen-Image-2.1。
- **4 种精度/量化**：fp16 / bf16 / int8 / fp8；**3 种 GPU**：RTX A6000、RTX 6000 Ada、H100 NVL；每套最多 100 条 prompt。
- 每个配置比较「单独生成」与「放进 batch 生成」，并跨 GPU 比较；记录 **bit-identity、MAE、SSIM、LPIPS**。
- **关键纪律**：文中所有 replay control 都是 **bit-exact**，因此变化不是采样噪声，而是执行设置（batch 组成与 GPU）造成的。

### 2.2 机制归因

「reduction orders change with tensor shapes, and 8-bit formats amplify small numerical differences into visible ones」——归约顺序随张量形状改变，8-bit 格式把微小数值差放大成可见差异。作者明确说这不构成完整的 serving 修复，**batch-invariant execution for image models 仍是开放问题**。

## 三、技术细节

### 3.1 跨模型 SSIM（对 batch-1 参考，1.0 = 完全相同）

| 模型 / 精度 | SSIM | MAE | LPIPS | 备注 |
|---|---|---|---|---|
| Emu3.5 bf16 | **0.580** | 30.16 | 0.168 | 自回归，10 条 prompt 全变 |
| Emu3.5 int8 | **0.551** | 31.78 | 0.229 | 量化再降 |
| Janus-Pro-7B bf16（sampled） | **0.261** | 46.64 | 0.296 | 自回归 |
| Janus-Pro-7B bf16（greedy） | **0.229** | 54.77 | 0.319 | 贪心反而更差 |
| HiDream-O1 fp8 | 0.748 / 0.731 / 0.686 | 15.45 / 17.85 / 19.56 | 0.109 / 0.159 / 0.176 | stage 10 / 25 / 100 递降 |
| Qwen-Image-2.1 bf16 H100 | 0.873 | 7.476 | 0.068 | 同 GPU 也不同图 |
| Qwen-Image-2.1 fp8 H100 | 0.811（stage10）/ 0.820（25）/ 0.863（100） | 7.75 / 9.72 / 10.00 | 0.044 / 0.071 / 0.092 | fp8 放大 |
| FLUX 3 Klein bf16 / int8 | 0.998–0.999 | ≈0.13 | ≈0 | **唯 fp8 破例：0.829 / 0.855** |
| SDXL bf16 | 0.878（fp16 0.951） | 8.230 | 0.072 | 每张都变 |
| 扩散 bf16（若干模型） | 0.96–0.98 | — | — | 结构相近但**每张都不同** |

跨 GPU 差异与同 GPU 内 batch 效应**同一量级**（mean LPIPS 0.355–0.383 vs 0.347–0.381）。

### 3.2 三个必须记住的口径细节

- **bit-identity 全为 0.0**：所有列出的模型/精度下，单独生成与 batch 内生成**没有一张位相同**。
- **「大致一样」不等于「判定一样」**：bf16 扩散模型 SSIM 0.96–0.98 看似接近，但「changes every image」；文中还说多数情况下 batch 图是「a different but equally valid image」，少数（含数字、计数器的 prompt）**明显更差**。⇒ 图像级相似度不能替代逐样本风险判定。
- **有效比较数下限**：文中另有 `prompts overlap across the 192 pairs is exact`、P10/P25/P100 等权、SSIM 用 scikit-image 0.26.0 原生分辨率 RGB 且**丢弃 alpha 通道**——评测单位与实现细节都必须留痕。

## 四、实验与结果

### 4.1 作者自己列出的后果（原文口径）

> 「seeds do not make results reproducible, benchmarks and image-quality comparisons that mix batch sizes or hardware can be biased, and **safety audits and A/B tests on generated images need the serving setup reported**」

这条几乎是给本项目 6 版本看板写的：**只换流量比例不换尺子**之外，还要**不换 batch / GPU / bit 宽**，并把三者写进事件审计。

### 4.2 与 I2I 链路的直接关系

引言明确以**图像编辑**为例：编辑模型被要求「change one object in an image and to keep everything else the same」。若编辑前后的两次推理落在不同 batch 或不同精度，**「其余保持原样」这个判据本身就被执行环境破坏**。⇒ 本项目 I2I 改写分流 0/0% 的归因，除既有五种（判据无分辨率 / 改写没写好 / 抹掉要件 / 只读文本通路 / benchmark 允许单模态通关）之外，出现**第六种可证伪归因：编辑前后对照被 batch 非确定性污染，导致「改对了」永远无法被判定**。

### 4.3 结果判读

- 与 11-24「Vulnerability Window（4-bit 量化后 1.1–12.3% 成对判定翻转而聚合准确率只动 0.03 点）」构成**同一现象的上下游**：那篇测的是判定模型的量化，这篇测的是**生成模型**的执行环境；两篇合起来说明「量化/加速不劣化」必须同时覆盖生成侧与判定侧。
- 与 11-24「judge 配置指纹」合起来：版本间比较时要冻结的不只是 judge，还有 **serving setup 指纹**。

## 五、局限性

1. **只测像素/结构相似度，没测风险判定翻转率**：SSIM / LPIPS / MAE 不是安全率，不能直接换算成「图审会不会换结论」。本项目迁移时必须自己补「同一 prompt 跨 batch/精度下，图审判定翻转率」这一栏。
2. **6 模型 / 3 GPU / 4 精度**：未覆盖统一生成-编辑模型、未覆盖 T2V/I2V、未覆盖线上 vLLM/SGLang 连续批处理的具体实现。
3. **没有给出可部署修复**：文中明确「local interventions tested do not make the whole pipeline batch-invariant」，batch-invariant 执行仍是开放问题。
4. **风险语义未涉及**：数字/计数器 prompt 会「明显更差」是视觉质量观察，不是 NSFW / 政治风险结论。
5. **量化档不是 fp4**：覆盖 fp8 / int8，用户侧 fp4 需另做一档。

## 六、复现指南

### 6.1 论文复现

固定 prompt + seed，对每模型 × 精度 × GPU 组合，分别生成 solo 与 in-batch 两版，报 bit-identity / MAE / SSIM / LPIPS；SSIM 用 scikit-image 0.26.0、原生分辨率 RGB、丢弃 alpha；配 bit-exact replay control 排除采样噪声；按 stage（10/25/100 步）与 prompt 集分层报。

### 6.2 本项目最小复现（零训练，半天，最优先之一）

**用同一份改写后 prompt、同一 seed、同一权重**，在下列四格里各生成一次并过现有图审：

| 格 | batch | 精度 | GPU |
|---|---|---|---|
| A | 1 | 线上全精度 | 线上机 |
| B | >1（线上真实 batch） | 线上全精度 | 线上机 |
| C | >1 | fp8 / fp4 | 线上机 |
| D | >1 | 线上全精度 | 迁移目标机 |

**必报四栏**（缺一不可）：① 逐样本**图审判定翻转率**（按一级类目 × L2_30 分格）；② 分层宏平均 F1 与 `Δaggregate`/`Δmacro` 符号；③ 分语言分档安全率；④ TTFT / e2e / TPOT / 超时率 + **serving setup 指纹**（batch size、bit 宽、GPU 型号、缓存/步数配置）。

**判据**：任何格出现「SSIM ≥0.96 但逐样本判定翻转 >3%」⇒ 现有「同 prompt 对照」类 AB 结论按 serving setup 重算；shadow → canary → 全量每一步必须**冻结同一份 batch / 精度 / 硬件**，只换流量比例。

**写入事件审计**：把 batch size、bit 宽、GPU、缓存方法、步数作为**必填字段**加入策略命中事件落表与 6 版本看板配置指纹；否则「改写前后」「版本前后」的对照不可复现。

**I2I 专项**：对 2000 条图生图评测集（1979 有效样本）抽 200 条，把「编辑前后其余保持原样」的判定改成 **solo-vs-solo 强制同 batch 配置**，看 0/0% 命中率是否变化；若变化 ⇒ 第六种归因成立，先修评测执行环境，不要重写改写器。
