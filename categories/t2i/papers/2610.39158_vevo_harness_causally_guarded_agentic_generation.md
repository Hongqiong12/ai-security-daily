## 一、背景与问题

### 动机

视觉生成与编辑的瓶颈已经从"像素保真"迁移到"满足密集约束的用户规格"。工业界的应对是把生成器包进 agent 工作流，主流形态是一个 **generate–verify–rewrite** 的浅循环：生成一张、VLM 判一下、不对就改 prompt 再来一次。

论文指出这个循环有三处结构性缺陷：

1. **VLM 判断太粗。** 一个二值的"过/不过"没有归因，下游只能盲试。作者原话是"binary signals obscure … semantically grounded root causes"。
2. **修好的经验丢掉了。** 循环结束后什么都不留，下一个同类请求从头试错。
3. **不加门控地留下来会毒化技能库。** 一旦允许把"这次改法"写进持久库，错误经验会累积，最终 harness 级幻觉。

更狠的一句在 related work 里，直接对着我们这条路：

> "recent work shifts scaling from model weights to test-time computation, i.e. prompt densification and semantic rewriting. **However, prompt-only interventions lack fine-grained attribution and pixel-grounded feedback.**"

这句话是对"输入侧改写"这条范式的正式批评：**纯 prompt 干预没有细粒度归因，也没有像素级反馈。**

### 核心问题

1. 能不能把二值判断**加密**成可定位的根因？
2. 一条"修复经验"能不能在入库前**证明它真的有用**（而不是碰巧有用）？
3. 经验积累到几十上百条时，怎么防"技能库中毒"？

## 二、核心方法

### 四件套

| 组件 | 做什么 | 一句话 |
|---|---|---|
| **Visual Traceback**（视觉回溯） | 把稀疏的布尔判决加密成**根因归属**，用分层验证树 | 从"错了"到"错在哪一条约束上" |
| **Visual Continual Governance**（视觉持续治理） | 每条候选技能补丁入库前做**反事实双臂 replay**，只收因果效应为正的 | 从"改完变好了"到"因为改了这个才变好" |
| **Lifecycle-managed Harness State**（生命周期状态） | 把 episodic 经验按 working / experience / pattern 三层蒸馏成可路由的技能库 | 从"记流水账"到"提炼能力" |
| **Heterogeneous Sandbox Policy**（异构沙盒策略） | 三类修复原语组成的动作空间，按根因**成本感知**路由 | 从"一律重写"到"该重采样就重采样、该调参就调参" |

### 动作空间：这一条最关键

$$\mathcal{A} = \{a_{\text{rewrite}},\ a_{\text{resample}},\ a_{\text{tune}}\}$$

论文明确指出，既有 pipeline 采用**单一干预范式**，把所有视觉失败都归因为"prompt 没对齐"，于是只会改写。而失败有**异构因果来源**：

- 约束确实没被表达 → **该改写**
- 表达对了但这次采样运气差 → **该重采样**
- 表达对了、采样也对，但模型对这类细节能力不足 → **该调参**

**把这三类都当成"改写"，就是本文批评的"monolithic intervention"。**

### 反事实双臂 replay 的判据

设冻结生成器 $G$、视觉奖励 $R_{vis}$。对技能 $s_k$ 上的干预 $s_k \oplus \phi$，其反事实效用是**相对未打补丁技能的视觉奖励期望偏移**：

$$u(\phi) = \mathbb{E}_z\big[R_{vis}(G(z; s_k\oplus\phi)) - R_{vis}(G(z; s_k))\big]$$

**只收入 $u(\phi) > 0$ 的补丁。** 这个判据很朴素，但它是"入库"这个动作唯一的把关点 —— 后面看到的入库质量差异全部来自这里。

## 三、技术细节

### 三处工程设计的价值

1. **分层验证树 + 逐约束回溯**：一次失败被拆到"哪一条约束没过"，而不是"整体不合格"。这让后面的路由有依据。
2. **denied-change buffer（拒绝变更缓冲）**：记住"哪些方向已经试过并失败"，避免反复 replay 同一个失败方向。论文实测这一项把 VLM 调用量**降 25.7%**（不带缓冲反而涨 71.8%）。
3. **lazy gating（惰性门控）**：只在低置信样本上多做一次判定，VLM 调用**降 47.5%**，性能**+0.28%**。

### 成本账（完整版）

| 配置 | 准确率 | 墙钟延迟 | VLM 调用数 |
|---|---|---|---|
| 完整版 | **84.38%** | **38.4 s** | **6.2** |
| 去掉惰性门控 | — | 45.2 s（−3.96% 性能） | — |
| 去掉反事实重排 | — | — | −1.80% |
| 去掉 EMA 更新 | — | — | −2.62% |
| 去掉方差正则 | — | — | −1.97% |
| 去掉成功保留 | — | +43.8 s | 不变（−2.75% 性能） |

论文的结论是：完整配置**同时是最准、最快、最便宜的**。这在 agent 系统里不常见（通常是"更准就更贵"），原因是惰性门控与拒绝缓冲把 VLM 调用压下来了。

| 门控方式 | 有害入库率 |
|---|---|
| 不门控（No Gate） | **33–40%** |
| 纯文本门控（Text-only Gate） | 约 **16%** |
| 完整反事实门控（VCG） | 第 100 episode 时约 **2%** |
| 去掉拒绝缓冲 | 回升到 **10%** |
| 去掉成功保留 | 回升到 **8%** |

论文同时记录：不门控的配置性能在中期冲到约 78 后**塌到约 71.5**，最终比完整版低约 **15%**。原因是"未经验证的更新污染了技能库"。

**这组数字的意义**：纯文本门控只能把有害入库率从 33–40% 压到 16%，**再加"看图"这一步才压到 2%**。也就是说 **8 倍的差距来自"验的时候看不看图"**。

## 五、局限性

1. **"改写"在本文里只是三个动作之一，且不是最强的那个。** 这篇的立场是"纯改写不够"，所以它能给我们的**不是改写方法，而是"改写不该独自承担"的证据**。
2. **Kling/GPT-Image 级别的对比是通过 API 调的，版本会漂移。** Table 4 的 Nano-Banana-Pro 数字（61.1 / 48.0 / 37.6）随时间不可复现。
3. **Table 4 的列标题在 PDF 抽取时有串位**（Causal/Spatial/Logical/Factual 等子列），本文只引用前四列（RISE/KRIS/WiseEdit/GEditTemp），其余不引用。
4. **"因果效用为正"是个很弱的判据**：一次干预平均为正，不代表对每个 case 都对，也不代表它没有被别的因素混淆。论文用的是同一 backend 双臂 replay，比观察性对比强，但仍不是随机对照。
5. **依赖 VLM 做视觉奖励**，VLM 自身的偏差会直接变成"因果效应"的偏差。论文没有测奖励模型的敏感性。
6. **成本仍高**：38.4 s/请求、6.2 次 VLM 调用，是单次生成的数倍。论文的"最便宜"是**在 agentic 方法内部**最便宜，不是相对单次生成便宜。

## 六、复现指南

### 环境
- 冻结生成器（论文用 Z-Image-Turbo / Qwen-Image-2512；也支持 Qwen-Image-2.0）
- VLM judge（用于验证与归因）
- 三类修复原语：rewrite / resample / tune

### 最小复现路径
1. **先做"归因"这一层，不做技能库。** 把一次失败拆到"哪条约束没过"（逐约束打分），只记录分布。**这一步零训练**，能立刻回答"我们的 I2I 改写失败到底集中在哪类约束上"。
2. **再做"三类动作的收益分解"**：同一批失败 case 分成三组，分别只给 rewrite / resample / tune，看哪一组收益最大。论文的 HSP 消融（Rewrite-Only 输 4.0%）预测**rewrite 是最弱的那个**。
3. **最后才做门控入库**，并且必须同时跑 No Gate / Text-only Gate / 反事实门控三条对照 —— 只跑一条无法知道门控值多少。

### 关键超参
- 反事实门控判据：$u(\phi) > 0$
- 拒绝缓冲 + 惰性门控（两者合起来把 VLM 调用从 ~12 降到 6.2）
- 三层技能蒸馏：working / experience / pattern

## 附：对我们的三条硬约束

| 论文事实 | 对我们的含义 |
|---|---|
| 纯文本门控 16% vs 看图门控 2% | 我们的分流/改写验收若只看文本判定，**有害经验入库率会高 8 倍** |
| Rewrite-Only 输 HSP 4.0% | I2I 改写 0/0% 可能不是"改写没写好"，而是**把 resample/tune 的活派给了改写** |
| Promptist 在 GenEval2 上 −19.3% | 改写方法在组合性重任务上可能**负收益**，评估必须分任务类型报 |
