# 编辑失败的瓶颈不是"再做一次"，是"看不见该看的东西"

**论文主页**: https://arxiv.org/abs/2610.39664
**领域**: Agentic 图像编辑 / 判定器观测空间设计 / 成对（listwise）判定 / 验证记录作为证据
**作者**: Haiyang Xu¹, Tianyu Wang, Jialu Li, Jiteng Mu, Yuanjun Xiong, Jianming Zhang, Zhuowen Tu, Mingze Xu（¹实习期间于 Adobe Research 完成）
**机构**: **Adobe Research + UC San Diego**
**发布日期**: 2026-10-29（v1，cs.CV）
**分类**: defense
**模态归属**: T+I2I 指令式图像编辑 · **对齐 I2I 改写分流 0/0% 的判定侧缺口** · 也直接服务图审 AB 的方法学

---

## 一、背景与问题

### 动机

真实的编辑请求很少只要求一次编辑。给一句话：

> "把我移到画面左侧，镜头拉宽一点露出更多海滩，去掉后面走路的人，再调成日落光。"

现在的编辑模型会**完成一部分，静默丢掉另一部分**。Agentic 编辑系统试图用 plan-edit-judge 循环解决，但论文指出一个更基础的问题：

> **当一步失败了，它做的几乎都是"用同一套窄工具和同一个只看一眼的 judge 再试一次"。**

论文用一个反问把问题重新定位：一个专业修图师遇到同样请求会怎么做？**换工具，并且凑近看**。修图师不会"再试一次"，他会**换一种做法 + 更仔细地看**。

于是核心论断：

> 一个编辑 Agent 被**两个空间**同时限制住——
> **action space**（它能做什么）与 **judge 的 observation space**（它能看见什么）。
> 现有 agent 把**两个空间都做小了**。

### 为什么这篇对我们直接命中 0/0%

我们的 I2I 改写分流是 0/0%。我们用的是一个 **pointwise judge**：给它源图、编辑后图、指令，让它判"改对了没有"。

这篇论文的两条结论，直接打在这个设计上：

1. **pointwise → listwise，同一个 judge 涨 13.8 个点**（Qwen3.8-27B：72.1% → 85.9%）。我们用的是最弱的那个判定制度。
2. **没有哪个 judge 在所有编辑类型上都最好**（论文原话：`no judge is reliable across edit types`）。CLIP-I 在 Style & Effects 和 Geometry 上**等于或低于随机**。

⇒ **我们的 0/0% 有一个极简解释：单点判定 + 单一判据，在编辑这个任务上结构性地判不动。**

### 顺手还给了一个"数据自举会中毒"的硬证据

论文把 EditAgent 当数据引擎，产了 25.7K 条全通过会话，拿去全量微调两个编辑器。结果：

> **直接用 FLUX.2-klein-9B 自己生成的数据去训 FLUX.2-klein-base-9B，三个 benchmark 全部退化；用 EditAgent 过滤后的数据，全部提升。**

⇒ 这一条对我们"用自研模型输出做 SFT 数据"的路线是一个明确的警告：**不过 judge 的自举数据是负收益**。

## 二、核心方法

### （0）先做诊断基准，再设计系统

论文没有先设计系统再评测，而是**先造一个诊断基准，把两个空间各自的缺口量出来**，然后针对性扩张。

**诊断基准**：

| 项 | 规格 |
|---|---|
| 编辑集数 | **600** |
| 编辑类型 | **30 种细粒度类型**，每类 20 集 |
| 六大组 | Content · Style & Effects · Scene · Photometric · Geometry · Enhancement |
| 每集内容 | 1 张源图 + 1 条指令 + **2–4 个候选编辑** |
| 候选来源 | 通用编辑器（FLUX.2-klein-9B）采样 + 专用方法（掩码局部编辑 / 物体移除 / 光度算子） |
| 标注 | **5 名专业 Photoshop 修图师共同圈选**所有"可用候选"（可接受地完成了指令） |
| 术语 | 被圈中的候选集合 = **winner set** |

这个基准的关键是 **winner set 允许多个**。评测"判得准不准"变成"你选出的那个在不在这堆可用的里面"，而不是"你选的对不对那一张"。

### （1）诊断结论一：一个编辑器不够，多采样也不够

按 winner set 的构成给 600 集分类：

| winner set 构成 | 集数 | 占比 |
|---|---|---|
| 只有通用编辑器候选 | 254 | 42.3% |
| **只有专用方法候选** | **175** | **29.2%** |
| 两类都有 | 90 | 15.0% |
| **没有任何可用候选** | 81 | **13.5%** |

因为每集都含通用编辑器候选，所以：

- **通用编辑器在 256 集（42.7%）上失败**；
- **专用方法救回其中 175 集**。

**分组差异极大：**

| 组 | winner set 只有通用 | winner set 只有专用 |
|---|---|---|
| Style & Effects | **73.8%** | – |
| Enhancement | – | **72.5%** |
| Geometry | – | **66.7%** |

**"多采几个"能不能救？不能：**

| 投递池 | 投递编辑可用的比例 |
|---|---|
| 只有通用编辑器（多个样本 + 同一 VLM 挑选） | **45.2%** |
| 加入专用方法的池（同一 VLM 挑选） | **68.2%** |

在 296 集"恰好一个投递可用"的样本里，**217 集来自带专用方法的池**。

⇒ **结论：瓶颈在 action space 的宽度，不在采样次数。** 这一条与 10-30 那篇 Grounded Exploration 的"抽象语义脚手架零收益"是同一件事的两个侧面——**加"理解层"没用，加"可执行的能力"才有用**。

### （2）诊断结论二：串行重试是错的，并行搜索对

这是本文最反直觉的一条，因为它**与 T2I 生成的结论相反**。

T2I 领域已经证明"串行精化（sequential refinement）"能提升文图对齐。但编辑不是生成：

> **编辑必须对源图忠实。串行精化在不停地编辑自己的输出，小错误会累积。**

对照实验（同一编辑器 FLUX.2-klein-9B + 同一 judge Qwen3.8-27B，预算都是 4 次图像生成）：

| 策略 | 做法 | VLM 调用 |
|---|---|---|
| **串行精化** | 基于 VLM 反馈改 prompt，迭代编辑上一次的结果 | 3 次反馈 + 1 次终选 = 4 |
| **并行搜索** | 直接从**原图**出 2 个候选；都不被接受则改 prompt 再从**原图**出 2 个，然后选 | ≤ 2 |

盲测：144 条 Complex-Edit 样本（复杂度 1/4/8），5 名专业修图师。

| 结果 | 数 |
|---|---|
| 偏好并行搜索 | **102** |
| 偏好串行精化 | 28 |
| 平局 | 14 |
| **非平局中并行搜索胜率** | **78.5%** |

⇒ **用一半的 judge 调用，赢 78.5%。** 原因很朴素：**每个候选都直接从源图出发，误差不累积。**

### （3）诊断结论三：没有 judge 在所有类型上都最好

四个 judge，都是 pointwise（一次判一个输出），输入是源图 + 编辑图 +（除 CLIP-I 外）指令：

- **EditScore-72B**（微调奖励模型）
- **EditReward-7B**（微调奖励模型）
- **CLIP-I**（与源图的 CLIP 相似度）
- **Qwen3.8-27B**（pass/fail prompt）

指标 **Winner-Set Hit@1**：在 515 个"至少有一个可用候选"的集上，judge 给出的最高分候选落在 winner set 里的比例（平局共享得分）。

**分组结果（关键在最后一列）：**

| Judge | 最强组 | 最弱组 |
|---|---|---|
| EditScore-72B | 总体最好，**但只在 Scene 组最好** | – |
| Qwen3.8-27B | **三组最准** | **Photometric 只比随机高 5.2 点** |
| CLIP-I | **Photometric 与 Enhancement 最准**（正确答案变化小） | **Style & Effects 与 Geometry 等于或低于随机**（需要可见变化） |

⇒ 论文的推论一句到位：**`What a judge must observe therefore depends on the edit.`**

**"那微调一个奖励模型行不行？"——不行：**

| Judge | Pointwise | Listwise（本文） | Δ |
|---|---|---|---|
| EditScore-7B | 65.9 | – | – |
| EditScore-32B | 68.0 | – | – |
| EditScore-72B | 70.3 | – | – |
| EditScore-7B, Ensemble@4 | 72.7 | – | – |
| EditScore-32B, Ensemble@4 | 73.3 | – | – |
| **EditScore-72B, Ensemble@4** | **76.3** | – | – |
| Qwen3.5-27B | 71.7 | **85.2** | **+13.5** |
| **Qwen3.8-27B** | 72.1 | **85.9** | **+13.8** |
| Gemma-4-31B | 73.8 | **86.1** | **+12.3** |

⇒ **现成 VLM 一旦能成对比较，直接超过在大量人工偏好标注上微调的 EditScore-72B（即使它做了 4 路集成）。** 论文的说法：`Such comparative judging is not supported by EditScore models, which are finetuned with specific input and output formats.`

### （4）EditAgent：同时扩张两个空间

**扩张 action space —— 能力池（除通用编辑器外）：**

1. 掩码局部编辑与重上色（在 SAM 2.1 mask 内跑通用编辑器）
2. 物体移除（OSOR）
3. 物体移动（专用模型）
4. 主体缩放（分割 + 合成）
5. 全局与局部光度算子
6. 风格滤镜与神经风格迁移
7. 翻转、旋转、旋转至水平
8. 放大（裁剪 + 超分）与缩小（outpainting）

**扩张 observation space —— verification record（验证记录）：**

核心洞察：**不同的编辑需要核查不同的属性。**

> 局部编辑要同时核查"目标变化"与"无关内容保持"；几何变换要评估"方向与幅度"。

于是对每个候选收集两类信息：

- **代码能查的**：程序化检查的结论（变化图、编辑区域特写、测得的颜色与几何量）；
- **仍需视觉判断的**：把"剩下什么需要人眼判"也写进记录。

把「指令 + 源图 + 所有候选 + 各自的验证记录」一次性给 judge。

**流程：** planner 拆步 → analyzer 指定操作与目标 → grounder 用 VLM + SAM 2.1 定位 → router 选方法 → **各方法并行出候选（每步最多 3 个，每个方法至少 1 个）** → judge 一次 listwise 调用（随机顺序）→ 接受或给反馈重试（每步 2 次重试，每轮 2 次计划修订）。

**跨轮保护 —— history check：** 每轮结束后，把原图 + 之前各轮结果 + 当前图一起给 VLM，问"之前每条请求是否仍然成立"。**高置信违反时跑一次修复轮**，修复结果只有被 step judge 接受才采纳。

这一条解决的是 step judge 只看一步时"后面的编辑悄悄撤销了前面的编辑"的问题。

## 三、技术细节

### 主干与成本

- **planner / analyzer / grounder / judge 全部是 Qwen3.8-27B**；
- SAM 2.1 把预测框转成 mask；
- 两个 backbone：**Qwen-Image-Edit-2511** 与 **FLUX.2-klein-9B**。

### 三个评测基准

| 基准 | 规模 | 特点 |
|---|---|---|
| **EdiVal** | 572 个三轮会话 | 编辑质量随请求累积 |
| **Complex-Edit** | 8,496 条（真实 + 合成） | 指令复杂度分层 |
| **ComplexBench-Edit** | 763 条 | 组合式指令（并行约束 + 多步链） |

### 判定偏置的控制

Qwen3.8-27B 同时是内部 judge，作者**额外用 Gemma-4-31B 复跑了一遍**（Tab. S8）以规避自评偏置。这个自查动作值得记一笔——大多数 agent 论文不做这一步。

### 评测分辨率

EdiVal 上两个 backbone 都以 **512px 输入**编辑。因为多数闭源编辑器产 1024px 以上，作者**额外把 Qwen-Image-Edit-2511 跑 1024px 再缩回 512px** 做公平比较。

## 四、实验与结果

### 观测空间消融（全文对我们最有用的一张表）

Qwen3.8-27B 作 judge，Winner-Set Hit@1（%），三组逐步扩张观测空间：

| Listwise | Evidence | Style | Content | Scene | **Photo.** | Geom. | **Enh.** | **All** |
|---|---|---|---|---|---|---|---|---|
| – | – | 84.4 | 81.7 | 67.5 | **54.2** | 66.4 | **65.0** | **71.6** |
| ✓ | – | 87.1 | 87.1 | 72.0 | **47.2 ↓** | 78.6 | **36.8 ↓↓** | 73.6 |
| ✓ | ✓ | 87.6 | 86.4 | 81.9 | **64.4** | 81.4 | **80.3** | **81.3** |

**这张表里藏着一个极易被忽略的负结果：**

**只加 listwise（成对比较）会把 Photometric 从 54.2 打到 47.2、把 Enhancement 从 65.0 打到 36.8。** 也就是说，**在"正确答案与源图差异很小"的两组上，并排比较反而有害**——因为 judge 会被"视觉上更不一样"的那个候选吸引过去。

这正是 CLIP-I 在 Style & Effects / Geometry 上崩掉的镜像：**同一件事，两个方向都错。**

- 需要**可见变化**时（Style / Geometry）：judge 会偏向"没怎么变"的候选 → CLIP-I 崩；
- 需要**保持原样**时（Photometric / Enhancement）：judge 会偏向"变得多"的候选 → listwise 崩。

⇒ **成对比较不是免费的。它把"判定偏置"从"趋向保守"换成了"趋向显眼"。**

**只有把证据补上，两组才被救回来**：Photometric 47.2 → **64.4**（超过 pointwise 的 54.2），Enhancement 36.8 → **80.3**（远超 65.0）。总体 71.6 → **81.3**，比最强的微调奖励模型 EditScore-72B（74.8%）高 **6.5 点**。

### 跨 judge 泛化

**七个现成 VLM judge，加上验证记录后全部提升 6.3–9.3 点。**

| | 无记录 | 有记录 |
|---|---|---|
| 能否达到 EditScore-72B（74.8%） | **没有一个达到** | **每一个都超过** |
| 最强 | – | **Qwen3.8-Flash-Next 82.8%（+8.0）** |

⇒ 这条是"方法而非骨干"的证据：**同一条记录，七个不同模型的收益幅度一致。**

### 编辑质量提升（EdiVal）

## 五、局限性

1. **成本是 12× 量级。** Qwen 上 12.9 H100·h vs 单独编辑器 1.1 H100·h。虽然是"低于最强 agent 对手"，但相对基线是**十倍以上**的开销。生产环境是否接受取决于场景。
2. **诊断基准只有 600 集、30 类型，且是自建。** 未释放（论文只说要放）。且"可用候选"由 **5 名专业修图师共同圈选**——这种标注成本决定了它很难被第三方复现或扩展。
3. **judge 就是 planner，用的是同一个 Qwen3.8-27B。** 作者用 Gemma-4-31B 复跑规避自评偏置，但**这只排除了"judge 偏爱自己规划的结果"，没排除"规划器与判定器共享同一套盲区"**。这是 agent 系统里一个更深的耦合，论文没有触及。
4. **验证记录是手写规则集合，不是学出来的。** 哪种编辑要查哪些属性、代码怎么查，都是按编辑类型人工定义的（Fig. 4）。⇒ **新增编辑类型就要新增核查代码**，扩展性受限。
5. **安全维度完全缺席。** 全文的目标是"编辑质量"，没有任何一条涉及"这个编辑请求该不该做"。⇒ 对我们来说它是**判定方法学**的来源，不是安全方法的来源。
6. **listwise 在 Photometric / Enhancement 上的负面结果只被"补证据"绕过，没有被真正解决。** 论文没有给出"什么时候该用 listwise、什么时候该用 pointwise"的判定规则。⇒ 这个选择目前靠人。
7. **单指令 → 多步的 planner 质量未被单独评测。** 计划本身的错误（拆错步、顺序错）与候选质量的错误被混在端到端分数里。

## 六、复现指南

### 最小可复现路径（给我们自己用）

**实验一：pointwise → listwise（半天，零训练，最该先做）**

```
输入：同一批 (源图, 编辑指令, K=4 个输出)
条件 A（现状）：逐个判 "这个输出改对了吗" → 取最高分
条件 B：一次判 "这 4 个里哪个改得最对" → 取第一名
指标：与人工标注的一致率 / Winner-Set Hit@1
```

判据：**B − A ≥ 10 点 ⇒ 0/0% 的分母是判定方式，先改判定再改改写。**

对标锚点：Qwen3.8-27B **72.1 → 85.9（+13.8）**；Gemma-4-31B **73.8 → 86.1（+12.3）**。

**注意：必须选 K ≥ 2。** K=1 时 listwise 退化成 pointwise，这是最容易做错的一步。

**实验二：加验证记录（1 天）**

不需要复现 8 种专用方法。只需要给每个候选附上**代码能查的那部分**：

```
对每条 (源图, 指令, 输出)：
  · change map（源图与输出的像素差热图）
  · 编辑区域特写裁剪
  · 测得的颜色直方图距离 / 主体 bbox 位移量
  · 程序化检查结论（"指定区域是否变化"/"非编辑区是否保持"）
```

判据：**对照"只有 listwise"的配置**。如果我们的编辑类型里有大量"正确答案变化很小"的（改光、增亮、微调饱和度），**listwise-only 会掉点，加记录才回来**。这是 Photo.(54.2→47.2→64.4) 与 Enh.(65.0→36.8→80.3) 的复现目标。

**实验三：并行 vs 串行（1 天）**

同一预算（4 次生成），A：串行精化（改 prompt 迭代编辑上一次结果）；B：并行从原图出候选。人评非平局胜率。判据：B 胜率接近 78.5% ⇒ 我们现在的"重试"逻辑在累积误差。

### 结构化拒绝理由 / 验证记录的落地顺序

不要一次做 8 种方法。按"我们实际会遇到的编辑类型"排序，先做**两类极端的核查**：

| 组 | 正确答案的特征 | 该加什么证据 |
|---|---|---|
| **Style & Effects / Geometry** | 需要**可见变化** | 变化幅度是否达标（change map 面积 / 位移量），防止 judge 偏向"没怎么变"的候选 |
| **Photometric / Enhancement** | 需要**保持原样** | 非编辑区的一致性（PSNR/SSIM 分块），防止 judge 偏向"变得多"的候选 |

⇒ **这两类恰好是"判定偏置"的两个相反方向，必须用两套证据分别兜。** 只做一套会救一头害另一头。

### 需要注意的实现坑

1. **Winner-Set Hit@1 需要"多可用候选"的基准。** 如果我们的标注只有"对/错"单标签，就无法复现这个指标。要么改成"至少一个可用"的判定，要么退回人工一致率。
2. **judge 的候选顺序必须随机化。** 论文明确写了 `shown to the judge in random order`。顺序不随机，judge 有位置偏置（这一点 10-29 那篇 VLM 拒答已给出 8–15pp 的位置效应）。
3. **history check 的触发阈值要保守。** 论文只在"高置信违反"时修复，且修复轮必须被 step judge 接受才采纳。放宽阈值会引入新的误差累积。
4. **数据自举必须先过 judge。** 不过滤是负收益（三个指标全降），这条可以直接写进我们的数据 pipeline 规范。
5. **别把成本当成次要因素。** 12× 的推理开销决定了这套方法只适合"离线批量处理"或"高价值单次请求"，不适合在线低延迟。

### 一句话结论

> **编辑失败的救法不是"再来一次"，而是"换一种做法 + 看得更细"。我们的 0/0% 缺的正是后半句。**
