## 一、背景与问题

### 动机

现在编辑图片越来越多是 agent 在做：把图和指令丢给一个开放编辑模型，让 VLM judge 判"改对了吗"，不对就再来一次。这个 loop 里，开放模型之间的成本差**超过一个数量级**：

| 模型 | 步数 | 单次生成耗时 |
|---|---|---|
| FLUX.2 [klein] 4B | 4 | **5.7 s** |
| Qwen-Image-Edit-2511 + Lightning | 8 | 39.8 s |
| FLUX.1 Kontext-dev + Turbo-Alpha | 8 | 25.7 s |
| Qwen-Image-Edit-2511 | 40 | **170.7 s** |
| LongCat-Image-Edit（CPU offload） | 50 | 108 s |
| Step1X-Edit v1.2（2 卡） | 28 | 173 s |

（24 GB RTX 4090D 实测）

所以"被拒之后下一步发给谁"直接决定成本与交付量。现有的三类做法——**同模型重试 / 每请求选一个模型的路由 / 固定顺序的级联**——都建立在同一个隐含假设上：

> **对已失败模型的下一次尝试，是一次独立同分布的重新抽样。**

论文把这条假设拆了。

### 我们为什么该看这篇

因为我们的 I2I 分流链路和它撞在同一个位置上。

我们的 I2I 改写分流当前命中 **0/0%**。前几轮我们把它归因为"没有可判的正例标准""改写抹掉了意图""下游能力不足"。这篇提供了一个我们没考虑过的第四种解释：

> **如果失败是"粘"的（sticky），那么"一次不过就记 0"这件事本身就在系统性地低估能力，而且会系统性地错排方法。**

它给的量化：**重试成功率只有首次成功率的 17%–53%**；按模型算是 **0.23–0.39 倍**。这意味着任何"单次通过率"都是个**上界被高估、下界被错估**的量。

### 核心问题

1. 怎么估计"给定失败历史后，某个模型下一次成功的概率"？
2. 怎么把估计变成"重试 / 升级 / 放弃"的动作，并且在负载变化时仍然成立？
3. **改写（rewrite）在这个 loop 里到底值多少？**

第三个问题是它顺手回答的，也是对我们最扎的。

## 二、核心方法

### （1）把 loop 建模成"失败状态上的规划"

一个请求 = (图, 指令)，由一串 attempt 服务。每个 attempt 选一个模型（arm），付"生成时间 + 一次 10 s judge 调用"，被 judge 判过或不过。请求在**首次通过**或**策略放弃**时结束。

状态 `s` = **到目前为止的失败计数向量**。定义 `p(a|s)` = 在状态 `s` 下，模型 `a` 的下一次尝试被接受的概率。最优策略解一个 Bellman 方程：

```
V(s) = min{  abandon,
            min_a [ c(a) + (1 - p(a|s)) · V(s + e_a) ]  }
```

其中 `c(a)` 是该 arm 的 GPU 秒数（含 judge）。扫不同的成本权重 `λ` 就画出一条 cost–success 前沿。

**关键对比**：同模型重试、每请求路由、固定级联，全都是把这个式子里的 `p(a|s)` 换成首次成功率 `p_first(a)`——**只有当重试独立时才精确**。

### （2）为什么失败是粘的：隐难度引理

论文给了一个引理，把"粘"这件事从现象变成机制：

> 设一个请求有潜在难度 `d`，arm `a` 的每次尝试在给定 `d` 下独立以 `p_a(d)` 成功。则失败历史只通过**失败计数**影响下一次尝试。

推论有两条，都很硬：

1. **重试永远不会比它前一次更容易成功**；当请求难度存在差异时，**严格更难**。
2. **当难度是共享的**（`d` 同时影响多个模型），一个模型的失败会**同时压低其他模型的成功率**。

第二条解释了文中一个关键数字：a5 在英文 GEdit 上首次通过率 0.733，失败一次后自己的下一次只剩 **0.143**，而**另一个模型 a4 在同样状态下还有 0.436**——不是 0.733，是 0.436。**失败这件事本身携带了"这题难"的信息。**

### （3）估计：计数 + 收缩

不拟合这个隐难度模型（因为 `p_a(d)` 没有参数形式），改成**直接计数**：

- 在日志里找「在状态 `s` 的所有 attempt 都失败」的训练请求；
- 取其中"下一次在 arm `a` 上通过"的比例；
- 深处状态样本稀疏，所以**按请求类别估计，再向全类别估计收缩**（Efron–Morris），收缩系数 `λ` 默认 **20**。

论文解释为什么不拟合：*"counts need no parametric form for p_a(d) and are most accurate in the shallow states that most requests visit."* ——多数请求只走到浅层状态，深层的参数化估计没有数据支撑。

### （4）规划：精确 DP + 负载感知

- 状态空间小：3 个 arm（上限 8/2/2）时 **81 个状态**；记忆化递归解精确解 **0.35 ms**（3 arm）/ **5.6 ms**（5 arm）。
- **负载感知重规划**：共享服务里打一个忙的 arm 还要付排队延迟。每次决策时把 arm 的期望等待与 judge 队列等待加进 `c(a)`，等待用 Little 定律估（队长 × 实测服务时间 / worker 数），然后**从当前状态重解一次**。
- **冷启动/漂移**：用 LinUCB + 一个 abandon 动作在线学。上下文 = 请求类别 + 各 arm 已失败次数 + attempt 序号；奖励 = 接受 − λ。

### （5）什么时候固定规则就已经最优（这一节最值得读）

论文给了两个命题，划清了"简单规则够用"的边界：

- **(i) 若重试独立** → 最优是**按"每次成功成本"升序**试各 arm，跳过性价比不行的，同模型重试只在单 arm 时最优。
- **(ii) 若失败只改变被失败 arm 自己的成功率** → **索引规则（index rule）最优**：每次选当前"每次成功成本"最小的 arm，超过阈值就停；此时"什么时候升级"有闭式答案。
- **(iii) 若难度共享** → **不存在通用的固定索引规则**。论文给了一个反例：70% 简单 + 30% 对两个 arm 都难，索引规则打 a→a→b 值 0.514，而在失败计数上规划的版本值 **0.560**。

**这条对我们最有用**：它说明"固定优先级/固定阈值/固定顺序"错在哪——不是错在参数没调好，而是**错在结构**。只有当"一个模型的失败不影响别的模型"时，固定优先级才对。而图像编辑里请求难度明显是共享的（同一张难图对所有模型都难）。

## 三、技术细节

### 实验规模

| 项目 | 配置 |
|---|---|
| 评测集 | GEdit-Bench **438** 条 / 11 类（中英各一套）、GEditBench v2 **230** 条、ImgEdit **180** 条 / 9 类 |
| 采样 | 最便宜 arm 8 seeds，其余 2 seeds；第 k 次尝试 = 第 k 个 seed |
| judge | **两个独立 VLM judge**：EditScore(Qwen3-VL-8B) + EditReward(Qwen2.5-VL-7B)；loop 内用两者分数分位数平均的集成 |
| 总图量 | **30,042** 张编辑图 |
| 分组 | 8 组（pool1 五组 / pool2 三组） |
| 成本权重 | `λ` 网格 |
| 离线回放 | 5 折，各自在 train fold 调参、test fold 报数 |
| 主预算 | pool1 **50 s** / pool2 **120 s**（约一次 a4 或 LongCat） |
| 服务台 | 3× RTX 4090D（a5 / a4 / judge 各一），160 条请求，两档稳态 + 一档突发，SLO **300 s** |

### 基线（11 个 + 2 个控制）

同模型重试、Best-of-N、**Rewrite-retry-blind**、**Rewrite-retry-critique**、CA-Routing、RouteLLM-SW、RouteLLM-MF、FrugalGPT、AutoMix、DiffServe、HADIS；控制组为"DP 但喂首次成功率"与"LinUCB 但无重试历史（ACQB 式）"。

两个 rewrite 基线的定义值得抄下来：

> *"Rewrite-retry, after the critique-and-revise pattern, has a vision-language model **rewrite the instruction before each retry of the cheap arm**, from the source alone (blind) or also from the failed edit and its score (critique)."*

**这就是一条完整的"改写→重试"策略，而且是被当强基线认真实现过的。**

### 收缩与 cap 的敏感性

- 收缩系数 `λ`：默认 20 附近都接近；**完全不收缩（λ=0）在 8 组里有 4 组显著变差**。
- 尝试上限：**cap 到 2 次在每一组都显著变差**；只给便宜 arm 一次机会在 8 组里 6 组显著变差。
- judge 阈值左右移：32 个偏移格子里 **30 个**仍不劣于最强基线。
- 训练数据降到日志的 **5%**，领先幅度仍为正。
- 把训练折的判定翻转（模拟标注噪声）：在任何测试噪声率下都不显著落后。

### （2）**改写 vs 重试：这是我们必须直面的那张小表**

只摘 pool1 的前四行（同一预算、同一 judge、同一批样本）：

| 方法 | GEdit-CN | GEdit-EN | Δ vs 同模型重试（CN / EN） |
|---|---|---|---|
| 同模型重试 | 81.74 | 81.74 | — |
| Rewrite-retry, blind | 80.82 | 82.42 | **−0.92 / +0.69** |
| Rewrite-retry, critique | 78.31 | 81.28 | **−3.43 / −0.45** |

三句话：

1. **"先改写再重试"≈"不改写直接重试"。** 盲改写在中英各 ±1 点以内；带失败反馈的改写反而**更差**（CN −3.43）。
2. 论文自己的结论原话：*"near the rewrite loop's own spend the two mostly tie, so the gain comes from spending the rest of the budget on escalation."* ——**收益不在改写，在于把剩下的预算花在升级上。**
3. 把改写**当成路由里的一个动作**呢？*"as one more action inside RetryRoute it never lowers success significantly and adds at most 2.2 points."* ——**上限 +2.2 点，且只是"不显著变差"。**

这是一个非常不舒服的结论。它的适用边界很重要，我在第五节会严格划出来。但**我们不能假装没看到它**：如果我们的评测把"改写"和"原 prompt 一次生成"比，我们报出来的收益里有相当一部分可能来自"多试了一次"，而不是"改得好"。

### （3）其余结果

- **领先幅度**：对最强基线平均 **+2.8 点**（最高 +5.6）；对同模型重试 **+3.5–13.3**。
- **APGR/AUC**：8 组全部高于每一个基线；**6/8 组的 APGR > 1**，即"在预算区间内收回的差距超过最便宜与最强单模型之间的全部差距"。
- **服务台 goodput**：三档负载下比最强基线高 **5.0–6.3 点**。
- **泛化**：留一类训练 → 8 组全部不低于最强基线；跨 benchmark 迁移 → 也全部不低于。
- **增益来源分解**：级联几乎从不重试，同模型重试从不升级；RetryRoute **两者都做**，且失败请求最少。
- **22 个 category×pool 对里 17 个为正。**

### （4）一个"判定器本身也不稳"的附带发现

> *"EditReward confirms 84–93% of the in-loop judge's **first-try** passes but only 51–75% of its **late** passes, those after a failure."*

**晚到的通过更不可信。** 在一个弱模型上反复尝试，会收集到"假通过"。这条和今天另一篇（Prompt Lottery）撞在同一个点上：**判定结果的可信度依赖于它是在第几次尝试产生的，而这个信息通常没被记录。**

## 五、局限性

### 论文自述的

1. **离线回放为主**。离线结果依赖日志覆盖的状态；深处状态样本少，靠收缩兜底。
2. **成本是 GPU 秒，不是钱**。真实服务的成本结构（冷启动、批处理、抢占）没建模。
3. **judge 是瓶颈也被当成了信号源**。整套策略默认 judge 的接受/拒绝是可信的——而第（4）条结果正是说它不太可信。
4. **只评了编辑任务**。生成任务的重试是否有同样的粘性，未验证。

### 我们迁移时必须自己划清的边界

**"改写无效"这个结论，不能直接搬到我们场景。** 三处关键差异：

| 维度 | RetryRoute 里的 rewrite | 我们的输入侧安全改写 |
|---|---|---|
| **目标** | 让编辑模型**听懂**（任务成功率） | 让审核/生成**不出事**（风险率），同时保住语义 |
| **失败判据** | VLM judge 判"改对了吗" | 标签/人工判"风险降了吗 + 语义还在吗" |
| **失败可观测性** | **完全可观测**（judge 每次都给分） | **不可观测**（用户是否被误伤，线上要很久才知道） |
| **反馈闭环** | 每次重试后立刻有新信息 | 一次生成结束，没有第二次机会 |

差异的后果：

- 它的 rewrite 失败，是"改写没帮模型听懂"；**我们的改写失败，是"风险没降下来"或"语义被改没了"。这是两种不同的失败。**
- 它的场景里"重试"是免费的第二次机会；**我们的场景里"让模型再生成一张"往往不被允许**（成本、时延、以及同一 prompt 再生成一次风险更高）。所以"用升级替代改写"这条路在我们这里**不成立**——我们没有"升级到另一个生成器"这个动作。

**所以正确的迁移不是"改写没用"，而是：**

> **改写必须跟"多试一次"这个基线比，而不是跟"什么都不做"比。**

这一条对我们的评测设计是硬约束。我们的三维评测（语义保真 / 安全提升 / 指令遵循）现在比的是「原 prompt」vs「改写后 prompt」。如果同一条原 prompt 多采几次就能拿到同等安全率，那改写报出来的收益是被"单次采样"这个设定虚高的。

## 六、复现指南

### 最小可跑版本

**不需要 GPU 服务台。** 纯离线回放就能验证最核心的一件事——"我们的失败是不是粘的"。

1. **准备日志**：同一批 I2I 样本（建议 200 条），每条用 **K=5–8 个不同 seed** 跑同一个编辑模型 + 同一个 judge，记录每次 pass/fail。
2. **算三个数**：
   - `p_first` = 第一次尝试的通过率；
   - `p_retry` = **第一次失败后**第二次尝试的通过率；
   - `ratio = p_retry / p_first`。
3. **判据表**：

| ratio | 含义 | 下一步 |
|---|---|---|
| **0.17–0.53** | 与论文一致，失败是粘的 | 我们的"单次命中率"全部需要重估；0/0% 要拆成"首抽 0%"与"能力 0%" |
| 0.6–0.9 | 轻度粘性 | 单次指标可作为保守下界使用 |
| **≈1.0** | 失败接近独立 | 论文结论**不适用**我们的链路，改写评测可以直接 vs 原 prompt 比 |
| >1.0 | 反常，可能 judge 有噪声/温度过高 | 先查 judge 稳定性，再谈策略 |

4. **再算第四个**：跨模型——`p(别的模型 | 本模型失败)`。若显著高于 `p_retry`，说明我们有"换条路"的空间（对应我们的多候选择优）；若不高，说明 0/0% 是难度问题不是路由问题。

### 实现坑

| 坑 | 处理 |
|---|---|
| seed 不独立（缓存/固定噪声） | 确认每次 attempt 真的换了随机源 |
| judge 阈值漂移 | 固定阈值，或按论文做法用两个 judge 的分位数平均 |
| 只用一次 attempt 就下结论 | 至少 5 次；cap=2 在论文里是显著变差的 |
| 把"晚到的通过"当同等可信 | 分别统计 first-pass 与 late-pass 的确认率（论文：84–93% vs 51–75%） |
| 预算不一致时横向比 | 必须同预算比，或报整条 cost–success 曲线 |

### 一个可以直接抄的工程动作

**在分流日志里加一列"这是第几次尝试"。** 现在我们的日志只知道"命中/未命中"，不知道"这是首抽还是重试"。加了这一列，才能算出上面那个 ratio——而在此之前，我们所有关于 0/0% 的讨论都缺这一维。
