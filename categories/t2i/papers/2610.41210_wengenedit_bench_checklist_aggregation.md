## 一、背景与问题

### 动机

真实的图像编辑请求很少是"把背景换掉"这一件事。它更常是：**换掉产品背景，同时保住包装盒上的文字和产品外观**。这时请求里至少有三个约束在同时生效——改什么（Edit Goal）、不许动什么（Preservation）、可以参考什么（Reference）。

论文把当前评测的病症命名为 **high-score paradox（高分悖论）**：

> 视觉上可信、或者单个最显眼的编辑成功了，**并不蕴含所有耦合的要求被联合满足了**。

一句话就够了：*"aggregate scores can readily obscure unmet local requirements"*。四个耦合要求里满足三个，整体分可以很高；剩下那个没满足的，在分数里看不见。

### 我们为什么该看这篇

三个理由，按重要性排：

**① 它是同行同场景。** 腾讯微信视觉做的编辑评测，评的模型名单里直接出现 `HunyuanImage-3.0-Instruct-Distil-CoT`、`GPT-Image-2`、`Seedream-5.0-Pro`、`Qwen-Image-Edit-2511`、`FLUX.2 [dev]`。它的口径、痛点、取舍和我们做 I2I 评测集（2000 条 / 1979 有效）时踩的是同一个坑。

**② 它给的正是我们缺的那件东西——"可判的正例标准"。** 我们的 I2I 分流是 0/0% 命中，前几轮的归因一直是"没有可判的正例标准，所以测不出东西"。这篇的做法是：**先把这个样本自己该满足的原子要件写出来，再让 judge 逐条判，最后才汇总**。这就是"正例标准"的生成方式。

**③ 它把"评测"接上了"训练"，而且是可控的。** `WeGenEvoStudio` 把评测输出的失败诊断转成"该补什么数据"的处方，再检索构数据、SFT、重评。这条链路正是我们"6 个模型版本迭代看板"想走的下一段。

### 核心问题

1. 整体分能不能代表"所有要求都满足了"？→ 不能，而且它系统性地**偏爱显眼的那一处改动**。
2. 有没有办法让"哪一条要求没被满足"变得可追溯？→ 有，把判定单位从"维度"下沉到"要件"。
3. 诊断出来的失败能不能直接驱动下一轮训练？→ 能，但要先解决"诊断粒度 vs 训练预算"的匹配问题。

## 二、核心方法

### （1）四个维度，但判定单位不是维度

评测分四维：

| 维度 | 全称 | 回答什么 |
|---|---|---|
| **EG** | Edit Goal | 要求改的，改到了吗 |
| **PR** | Preservation | 不该动的，动了吗 |
| **VQ** | Visual Quality | 画面本身是否成立（无明显崩坏/伪影） |
| **DS** | Domain-specific Capability | 该场景的专门能力（如文字渲染、参考绑定） |

关键在于：**这四个维度不是打分的起点，是汇总的终点**。起点是每个样本自己的一张 checklist。

### （2）预生成 checklist：把"语义"冻在评测之前

每个 instance 有一张**预生成**的 checklist，把请求拆成原子要件，分挂到 EG / PR / VQ / DS 之下。三个设计约束值得注意：

- **checklist 是"预生成"且"跨模型共享"的**。同一道题，所有被评模型用同一张 checklist。这排除了"judge 看模型下菜"的自由度——也是它能跨 15 个配置比较的前提。
- **checklist 是"sample-specific"的，由源图决定**。论文强调 general image editing 需要 *"sample-specific criteria grounded in source images"*，因为"该保住什么"取决于原图里有什么。
- **judge 必须先写理由和扣分，再给维度分**。原文：*"A fixed vision-language model (VLM) judge must record item-level rationales and deductions before assigning dimensional scores."*

### （3）判定协议：先要件、再维度、最后 Overall

```
每个 output
  ├─ 逐条判 applicable 的原子要件 → 每条给 pass/fail + 视觉证据理由
  ├─ 不适用的要件排除出分母（不记 0）
  ├─ 由要件结果汇总成 EG / PR / VQ / DS 四个维度分
  └─ 由维度分加权成 Overall
```

两条容易被忽略的纪律：

- **"一侧（side）通过"的定义是"每一条适用要件都过"**。原文：*"A side passes only if every applicable item scores ≥ τ; empty image-side lists are not successes."* ——**空列表不算成功**。这一句堵掉了一类很常见的刷分：模型什么都不交，或交了个空结构，被当成"没有违反要求"。
- **"高分输出"与"严重项"分开统计**。原文：*"High-scoring outputs have Overall ≥ ...; severe items score ≤ ..."*。也就是说不只看均值，还看"整体分很高但存在严重单项"的比例——这正是"高分悖论"的量化。

### （4）WeGenEvoStudio：把诊断变成数据处方

四段闭环：

1. **Diagnosis Agent**：输入是类别统计 + item 级理由 + 跨案例视觉复核，输出"任务级数据处方"（该补哪类任务、缺什么概念、源图从哪来）。
2. **Construction Agent**：按处方检索新概念与源图，合成定向编辑指令与配对训练样本。
3. **Supervised adaptation**：在目标模型上做受控的监督适配。
4. **Re-evaluation**：重评，刷新下一轮学习优先级。

**关键设计：受控。** 论文在实验里明确"报告选定的 Top-5 目标"与"全量"两组数字，就是为了把"定向收益"和"整体溢出"分开——这个拆分是整篇最实用的工程习惯。

## 三、技术细节

### 规模与口径（可直接对照我们的评测集）

| 项目 | 数值 |
|---|---|
| 评测 instance | **2,740** |
| 任务类型 | **148**（三个场景：单图编辑 / 文字密集编辑 / 多参考编辑） |
| 被评配置 | **15** 个 |
| 审计覆盖 | **15,214** 条 model–task 记录、**194,836** 条 item 记录 |
| 被排除的不适用项 | **262** 条 |
| 文字编辑同题对比 | 6 个模型在**同一批 920 个任务**上比 |
| 人工审计比例 | 每个 benchmark **随机 10%**，由 **3 名受训专家**审 |

我们横过来看：我们的 I2I 评测集是 2000 条 / 1979 有效，**没有"任务类型"这一层**，也没有 item 级记录。这两点差异直接决定了"出问题时能不能归因"。

### 版本管理与重评协议

这是全文对我们最有工程价值的一段。审计发现问题后的处理顺序是：

1. **先改 checklist**，不是先改分数；
2. **所有被比较过的模型，在同一份修订后的 checklist 上重评受影响的那批 case**；
3. 每个版本**同时冻结** judge、prompt、输入处理、checklist、无效响应策略这五项。

原文：*"Each version fixes the judge, prompt, input processing, checklist, and invalid-response policy."*

这五项冻结清单，正好是一份"多版本回归看板"的最小可信条件。少冻一项，"v3 比 v2 好"这句话就不成立。

### 一个诚实的边界声明

论文自己写明了审计的效力边界，这句值得抄下来：

> *"The audit corrects identified problems but does not independently validate every judgment or quantify accuracy gains over holistic evaluation. Inter-rater agreement and error rates cannot be inferred from this corrective audit."*

即：**这个 10% 审计是"纠错"，不是"验证"**。它不能给你 κ，也不能证明 item 级判定比整体判定更准。**它是一个质控动作，不是一个效度证据。** 这一点在传播时最容易被夸大。

### 评分与适用性

- 不适用的要件**排除出分母**，不记 0——避免"样本简单所以分高"。
- 任务标签重叠**不会让同一 instance 在 Overall 里重复计**。
- 论文明确写：*"The weights define an operational rubric."* ——**权重是一份运营口径，不是一个客观真值**。这句话把"Overall 4.076 是不是绝对水平"这个问题直接关掉了。

## 四、实验与结果

### （1）单图编辑：整体排序与维度排序不一致

| 模型 | EG | PR | VQ | DS | **Overall** |
|---|---|---|---|---|---|
| **GPT-Image-2** | **4.298** | 4.049 | **4.463** | 4.182 | **4.076** |
| Seedream-5.0-Pro | 4.207 | **4.084** | 4.434 | **4.206** | 4.029 |
| Nano-Banana-Pro | 4.159 | 3.752 | 4.370 | 4.050 | 3.882 |
| HunyuanImage-3.0-Instruct-Distil-CoT | 4.071 | 4.065 | 4.265 | 4.008 | 3.862 |
| HunyuanImage-3.0-Instruct-Distil | 4.020 | 4.175 | 4.280 | 3.952 | 3.841 |
| Qwen-Image-3.0 | 4.120 | 3.469 | 4.331 | 4.126 | 3.813 |
| FireRed-Image-Edit-1.1 | 4.091 | 3.550 | 4.227 | 3.902 | 3.736 |
| JoyAI-Image-Edit | 4.042 | 3.547 | 4.169 | 3.794 | 3.667 |
| Qwen-Image-Edit-2511 | 3.963 | 3.567 | 4.095 | 3.708 | 3.588 |
| FLUX.2 [dev] | 1.964 | 3.418 | 3.555 | 2.154 | 1.967 |

**读法一（最要紧的）**：`HunyuanImage-3.0-Instruct-Distil` 的 **PR = 4.175，全场最高**——比 Overall 冠军 GPT-Image-2 的 4.049 还高。但它的 Overall 只有 3.841，排第五。

> 也就是说：**一个模型可以在"不该动的没动"这件事上做到全场第一，同时整体排第五。** 整体分把这个"第一"吃掉了。

**读法二**：`Qwen-Image-3.0` 的 DS = 4.126 高于 GPT-Image-2 的 4.182？不，低于。但它的 DS 高于 Seedream 的 4.206？也低于。它的 EG = 4.120 高于 Hunyuan 两个版本（4.020 / 4.071），Overall 却低于它们（3.813 vs 3.841 / 3.862）。**EG 更好、Overall 更差**——因为 PR 是 3.469，全场倒数第二。

**结论**：这张表本身就是"聚合把局部结论翻掉"的现成证据。它不需要额外实验证明。

### （2）跨维度权衡：涨 0.373，同时跌 0.343

Qwen-Image-Edit-2511 经过 WeGenEvoStudio 适配后：

- Overall **+0.373（+13.2%）**
- 但表内同时出现 **−0.128** 与 **−0.343** 两个维度/子项跌幅

FLUX.2 [dev] 更极端：Overall 从 **1.083 → 3.517（+2.434）**，但同表内的分维度增量从 **−0.343** 到 **+4.524** 跨度极大。论文把这一节直接命名为 *"Backbone-dependent adaptation and cross-dimensional trade-offs"*——**适配是换了一组能力，不是整体变强**。

### （3）定向收益 vs 全量溢出：这是最该抄的实验设计

| 模型 | 数据集 | 定向 Top-5 | 全量 | 定向/全量 |
|---|---|---|---|---|
| Qwen-Image-Edit-2511 | WeGenBench | **+0.968** | +0.670 | 1.44× |
| Qwen-Image-Edit-2511 | WeGenEditBench-Single | **+0.373** | — | — |
| FLUX.2 [dev] | WeGenBench | **+0.230** | +0.124 | 1.85× |
| FLUX.2 [dev] | GEdit | **+3.944** | +3.009 | 1.31× |
| FLUX.2 [dev] | ImgEdit | **+1.362** | +1.269 | 1.07× |

**定向收益普遍是全量收益的 1.07–1.85 倍。** 换句话说：**只报全量，会把定向干预的效果稀释掉一半。** 反过来，只报定向，会把"过拟合到诊断目标"这件事藏起来。两个数必须一起报。

### （4）跨 benchmark 迁移：诊断能迁移，收益不能

FLUX.2 在五个 report-selected GEdit 类目上训 2,346 步后用 GPT-4.1 VIEScore 评：

| 类目 | SC | PQ | O | ΔSC | ΔPQ | ΔO |
|---|---|---|---|---|---|---|
| motion_change | 8.114 | 8.430 | 7.907 | +5.747 | +0.848 | +5.295 |
| subject-remove | 7.272 | 8.316 | 6.911 | +3.991 | +0.351 | +3.706 |
| color_alter | 9.275 | 7.812 | 8.308 | +5.463 | +0.050 | +4.371 |
| material_alter | 7.625 | 7.600 | 7.002 | +4.438 | +0.575 | +3.678 |
| subject-replace | 7.817 | 7.933 | 7.226 | +3.658 | +0.425 | +3.173 |

注意 ΔSC（语义一致性）涨幅 3.7–5.7，而 **ΔPQ（感知质量）只有 0.05–0.85**。**诊断驱动的数据合成能大幅拉起"做对没做对"，几乎动不了"好不好看"。** 这是个很符合直觉、但很少有人分开报的结果。

## 五、局限性

### 论文自述的

1. **审计不构成效度证据**。10% 人工审计是纠错，不能推 κ、不能推错误率（§3 已引原文）。
2. **权重是运营口径**，不是客观真值。换个权重，Overall 排序可能变。
3. **它假设 judge 有能力执行 checklist**。整篇的可信度压在"固定的 VLM judge 能逐条判原子要件"这一个前提上——而这个过程本身没有被独立验证。
4. **RSI 部分是小规模验证**。15 个配置、Top-5 目标集，不是"通用自我进化"的证据。

### 我们自己该补的

- **它是编辑质量评测，不是安全评测。** 148 个任务类型全部是"编辑做对了没"，没有一条是"这个编辑请求该不该被执行"。所以它解决的是我们**下游能力**那一半，不解决**上游分流**那一半。
- **checklist 的生成过程在正文里被压缩了。** 谁写的、用什么模型写的、人工校准到什么程度、一个 instance 平均几条要件——这些决定了"原子要件"是不是真的原子。我们若要复用，必须自己标定这一步。
- **没有延迟/成本口径。** item 级判定意味着每个样本的 judge 调用量上升数倍。194,836 条 item 记录 / 2,740 任务 ≈ **平均每题 71 条 item 记录**（含 15 个配置，即**每配置每题约 4.7 条要件**）。这个量级在离线评测可接受，在线上分流不可接受。

## 六、复现指南

### 最小可跑版本（不需要 2,740 条）

1. **先从现有 1979 条 I2I 评测集里抽 200 条**，覆盖你能想到的所有任务类型；先不追求 148 类，能凑 20–30 类就够验证机制。
2. **给每条写 checklist**：人工 or 强模型起草 + 人工审。参考四维：EG（要改什么）/ PR（不许动什么）/ VQ（画面是否成立）/ DS（场景专长）。**每条要件必须能被一张图的是/否回答**——写不成这样就不是原子要件。
3. **先做"预生成 + 跨模型共享"**：同一张 checklist 打所有候选改写版本。这一条不做，后面所有对比都无效。
4. **冻结五项**：judge 模型、judge prompt、输入预处理、checklist 版本、无效响应策略。
5. **先只报两个数**：① 每维度的要件通过率；② "整体高分但存在严重单项"的样本比例。**这两个数出来之后再看 Overall**。

### 关键实现坑

| 坑 | 表现 | 处理 |
|---|---|---|
| 要件不原子 | 一条要件里塞了两个条件，judge 判"部分满足" | 拆开；或强制二值 + 写理由 |
| 不适用项被记 0 | 简单样本被系统性压低分 | 排除出分母（论文做法） |
| 空输出算通过 | 模型交空结构刷分 | "every applicable item must pass；空列表不算成功" |
| checklist 随模型变 | 每个模型一张表，比较失效 | 预生成 + 共享 |
| 只报 Overall | 局部缺失被吃掉 | 强制同时报 4 维 + 严重项比例 |
| 只报全量 | 定向干预被稀释 1.07–1.85 倍 | 定向 Top-K 与全量必须成对报 |

### 迁移到我们场景的最小改动

不需要重做评测集。**在现有 1979 条上补一层"要件"即可**：

- 对每条 I2I 样本，抽出「主体 + 操作 + 目标区域 + 必须保留项」四类要件（正好对应 StruPO 的 DSE 三锚点 + PR 维度）；
- 让 judge 逐条判，记录 item 级结果；
- 把"分流命中率 0/0%"这个单一指标，替换成**"要件覆盖率"**——即"这条指令的要件被完整读出的比例"。

这一改，0/0% 就从一个 0 变成四个数：要件全没读出 / 读出部分 / 全读出但下游没执行 / 全读出且执行。**这正是我们前几轮一直想要的归因分辨率。**
