## 一、背景与动机

### 动机

用 RL 训练一个 **rewriter**（语言模型），让它为**冻结的图像生成器**改写 prompt，已经成为 T2I prompt engineering 的主流范式——这也正是当前业务里 T2I 安全改写模型的技术形态。

但现有 RL 方法有一个结构性错配：

> 奖励信号是**从整张图**算出来的（image-level single signal），却被**平摊到每个 subword token**上。

而自然语言 prompt 里，真正的语义单元不是 subword，而是**连贯的语义 span**：

- 一个**物体**（"a red vintage car"）
- 一个**数量**（"three birds"）
- 一个**属性**（"glossy, matte"）
- 一个**关系**（"to the left of the table"）

把整图奖励摊到 subword，等于强迫信用分配去解一个它本来不该解的问题。

### 核心科学问题

能否让 RL 的更新权重**对齐 prompt 的语义结构**，而不是对齐 tokenizer 的切分结构？

### 对当前业务的重要性

⭐ **这是今天与业务技术栈最贴身的一篇。**

业务的 T2I 安全改写正是「LLM rewriter + 冻结图像生成器 + RL 优化」的形态（奖励来自 Qwen-Image 一致性）。SCOPE 直接改进的就是这个链条里的**信用分配层**。

而且它指向一个更关键的洞察：**安全改写的"语义保真"要求，本质上就是"不要在错误的语义单元上分配信用"。** 如果改写把"性感"改成了"优雅"，我们希望 RL 知道这是**一个 span 的替换**，而不是一堆 token 的各自漂移——这正是 SCOPE 的归纳偏置。

---

## 二、核心方法

### SCOPE（Semantic Bounded Credit Optimization）

基于 **GRPO（Group Relative Policy Optimization）** 改造目标函数，让更新权重对齐语义 span 结构。

**核心机制三步：**

**（1）rewriter 联合生成两样东西**
- 增强后的 prompt（enhanced prompt）
- 该 prompt 的**语义划分**（semantic partition）

即：模型输出改写文本时，同时输出"这句话由哪些语义 span 组成"。

**（2）span 内池化策略 log-prob 偏移**
在每个语义 span 内部，把各 token 的 policy log-probability 偏移**池化（pool）**，得到该 span 的**共享系数**，用于加权该 span 内所有 token 的 loss。

**（3）保留 completion 级单一 advantage**
每个 completion 仍然只有一个 advantage（来自图像奖励），不做 span 级奖励分解。

### 设计上的克制之处

论文明确强调两点"不需要"：

- ❌ **不需要额外的 span 级奖励**（no separate span rewards）
- ❌ **不需要额外的图像渲染**（no additional image renders）

这意味着 SCOPE 是一个**纯目标函数层面的改动**，不增加数据构造成本、不增加推理采样成本。对工业 RL pipeline 来说这是最低侵入度的改造。

---

## 三、技术细节

### 为什么是"Semantic Bounded"

信用分配被**限定（bounded）在语义 span 内部**：span 内共享一个系数，span 之间不共享。这带来两个效果：

1. **span 内一致**：属于同一个语义单元的 token 会同进同退，不会被拆散学习；
2. **span 间可比**：不同 span 的系数可以互相比较，等价于给改写结果提供了一个"哪个语义单元贡献大"的隐式信号——虽然论文没把它显式用作可解释性工具，但这条信息是免费产出的。

### 与 vanilla GRPO 的差异

| 维度 | Vanilla GRPO | SCOPE |
|------|-------------|-------|
| 信用分配粒度 | subword token | 语义 span（共享系数） |
| advantage | 每 completion 一个 | 每 completion 一个（不变） |
| 额外奖励设计 | — | 无 |
| 额外渲染成本 | — | 无 |
| 额外输出 | — | semantic partition |

### 归纳偏置的本质

论文把"语义结构"明确定位为 **practical inductive bias for prompt engineering with RL**。这个定位很准：它不是新的 RL 算法，而是承认**语言的结构先验应该进入优化目标**，而不是让优化器自己从零学出来。

## 四、实验与结果

### 实验设置

- **三个冻结图像生成器**：Qwen-Image、SD3、FLUX.1-dev；
- 对比基线：vanilla GRPO；
- 评测基准：**GeneVal** 与 **T2I-CompBench**。

### 主要结果

| 基准 | 相对 vanilla GRPO 的平均相对增益 |
|------|--------------------------------|
| **GeneVal** | **+9.48%** |
| **T2I-CompBench** | **+7.62%** |

### 消融结论

论文明确指出两个因素**都对增益有贡献**：

1. **语义边界本身**（semantic boundaries）——即"有 span 划分"这件事；
2. **span 内池化**（pooling within spans）——即"span 内共享系数"这件事。

### 结果怎么读

+9.48% / +7.62% 是在**质量导向**（compositionality）的基准上拿到的，不是安全基准。但方法本身与奖励是什么无关——**奖励换成安全分/一致性分，机制照样成立**。这正是它可以平移到安全改写 RL 上的原因。

值得注意的是，Qwen-Image 在实验列表里——这与业务侧用 Qwen-Image 一致性做奖励是同一生成器，复现基础是现成的。

## 五、局限性

1. **只在质量维度验证，未涉及安全。** 论文做的 prompt engineering 是增强语义完整性，不是安全改写。把奖励换成安全奖励后，span 划分是否仍然稳定（尤其当风险锚点本身就是 span 时）需要实测。
2. **semantic partition 由 rewriter 自己生成**，其质量依赖 rewriter 能力。若划分错误，共享系数会把错误的语义单元绑在一起，可能放大而非抑制漂移。
3. **"平均相对增益"口径偏粗**，未给出方差/显著性，跨三个生成器的分解也未在摘要中披露。
4. **安全场景的 span 语义与质量场景不同**：质量场景 span 是"物体/属性/关系"；安全场景 span 是"风险锚点/修饰语/场景上下文"。划分标准需要重新定义。
5. **没有讨论与 edit rate 约束的交互**。业务侧用 clamped normalized Levenshtein 约束 edit rate，span 级信用分配与 token 级编辑距离约束如何共存，是开放问题。

## 六、复现指南

### 最小复现路径

1. 准备 rewriter（LLM）+ 冻结生成器（建议先用 **Qwen-Image**，与论文一致且与业务一致）；
2. 在 rewriter 的输出格式里增加 **semantic partition** 字段（例如用 tag 或分隔符标出 span 边界）；
3. 修改 GRPO loss：
   - 正常算每个 token 的 policy log-prob shift；
   - 按 span 分组做池化，得到 span 共享系数；
   - 用该系数量乘 span 内各 token 的 loss；
   - advantage 保持 completion 级单一值不变；
4. 奖励用图像侧指标（质量场景：GeneVal/T2I-CompBench 打分器；安全场景：安全分 + 一致性分）；
5. 与 vanilla GRPO 做同种子对照。

### 迁移到安全改写业务的具体建议

这是今天**最可直接上手实验**的一篇，建议改造点：

- **把 semantic partition 的定义换成安全语义单元**：风险锚点 span / 修饰语 span / 场景上下文 span / 风格 span。改写时希望"只动风险锚点 span，其余 span 系数趋近于不变"。
- **span 级系数天然可做诊断**：如果训练日志显示"非风险 span 的系数长期居高不下"，就说明 rewriter 在做无谓改写——这比只看最终 edit rate 更早暴露问题，可直接作为**训练期 early warning 信号**。
- **与 edit rate 约束协同**：可以把 span 级系数改造成"span 级 edit budget"，对非风险 span 施加更强的 edit 惩罚，而不是全局一刀切。这比全局 clamped Levenshtein 更精细。

### 环境依赖

- RL 训练框架（GRPO 实现，verl / trl 等均可改）；
- 冻结图像生成器推理服务；
- 无额外渲染、无额外奖励模型。
