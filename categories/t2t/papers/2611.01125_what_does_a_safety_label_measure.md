## 一、背景与问题

### 动机

情境安全（situational safety）benchmark 的做法是：给每个场景一个 SAFE / UNSAFE 标签，让 MLLM 回答问题，再判它的自由文本回答对不对，最后算个分。这些分**直接用于部署决策**。

论文问的是一个我们每天都在面对的问题：

> **这样一个 label score，到底在量什么？**

它给出一个三分的答案：这个分可能来自

1. **场景本身**（模型真的看出轨上站着人不安全）
2. **请求本身**（"怎么拍火车"这个问题自带风险语境）
3. **benchmark 自己的文件**（图片尺寸就把标签泄了）

第三种最荒谬，而且真的发生了。

### 两个先立住的现象

| 现象 | 数 |
|---|---|
| **文件泄漏**：MSSBench chat 的图片尺寸单独就能判对 | **82.3%**（95% CI [78.9, 85.5]），**追平或超过七个商用模型中的六个** |
| **修正后归零**：在修正过的 chat 划分上，尺寸规则掉到随机 | —— |
| **请求泄漏**：HoliSafe 上"只看请求、不看图"的分数，排对比值和看场景差不多 | AUROC 0.914（Molmo2-O-7B 的纯文本分） |
| **分区泄漏**：MOSSBench 的条目划分本身决定了标签 | —— |

这三条各自独立地说明：**label score 里有相当一部分不是模型能力。**

### 核心问题

1. 有没有一套**可测量的字段**，能把"这个分来自哪里"分开？
2. 把"排序能力"和"打标能力"分开之后，那个差可以怎么拆？
3. 拆出来的各部分，哪一部分**能靠调阈值修**，哪一部分**不能**？

## 二、核心方法

### （1）Benchmark Card：七个测出来的字段

对六个 benchmark 逐个填七格：

| 字段 | 量什么 |
|---|---|
| File-only rule | 只看图片文件能到多少（准确率/AUROC） |
| Metadata classifier | 只看元数据能到多少 |
| Request-only AUROC | 去掉图、只留请求 |
| Identical-request AUROC | 请求完全相同、场景不同时还能不能排对 |
| **Threshold / Overlap / Within** | Spot-Stop 三项分解（见下） |
| Recovery | 免标注修复能回收阈值项的多大比例 |
| Leakage verdict | 有没有泄漏、泄漏来自哪里 |

这张卡的价值不在"审计别人"，而在**它把"这个 benchmark 能不能用来做决策"变成了七个可查的数**。

### （2）Spot-Stop 分解：把 R − A 拆成三份

设：
- **R** = 排序指标（label score 的 AUROC）
- **A** = 打标指标（模型直接回答的 balanced accuracy）
- **零假设（label-swap null）** = 把标签随机交换后 R 的期望值（也就是"什么都不会"的基线）

**Spot-Stop gap** = R − A，即"会排序但不会打标"的那部分超额。把它拆成三份：

$$R - A = \underbrace{(A^* - A)}_{\text{阈值 part}} + \underbrace{(\mathrm{AUROC} - A^*)}_{\text{重叠 part}} + \underbrace{(R - \mathrm{AUROC})}_{\text{对内顺序 part}}$$

其中 $A^*$ 是**在最优共享切点上**能达到的准确率。三个 part 的含义是：

| Part | 定义 | 能不能靠调阈值修 |
|---|---|---|
| **Threshold** | 一个**共享的**切点还能救回多少 | **能**（这就是"阈值没调好"） |
| **Overlap** | 切点因为"安全分和不安全分重叠"而损失多少 | **不能**（信息本身不够） |
| **Within** | 只在**同一对**内成立的顺序 | **不能**（这是成对能力，不是绝对定标能力） |

论文还给了一个理论参照：如果分数是方差相等的双正态、AUROC 相同，则重叠项等于

$$g(\mathrm{AUROC}) = \mathrm{AUROC} - \Phi\!\left(\Phi^{-1}(\mathrm{AUROC})/\sqrt{2}\right)$$

实际重叠项**超过** $g(\mathrm{AUROC})$ 的那部分，说明"同一 AUROC 下分数的分布形状更差"。在 AUROC 0.77–0.90 区间内这个近似成立。

### （3）免标注修复：recentering

把阈值重设到**批次分数的均值**上（不用任何标签）。在平衡批次上，这一招能回收阈值项的大部分。论文实测：两种情况分别回收 **77%** 和 **99%** 的阈值项；在场景级的"同情境未标注场景"上 recenter，能让 **14 个模型里的 13 个**在 VSCBench 上排序变好，**+6.8 点 balanced accuracy、+0.069 AUROC**。

## 三、技术细节

### 分解的适用范围（这条限制很重要）

- 分解需要在**成对对比**（一个安全场景 + 一个不安全场景，请求相同）上做
- 在 MSSBench chat 上是 **600 对**；修正划分上是 **88 对**；六个 benchmark 共 1,200 对
- 对**没有成对结构**的 benchmark（表里有一列写 "no pairs"），只有 threshold 和 overlap 两项，没有 within 项

### 三个 part 在各 benchmark 上的中位切分（单位：点）

| Benchmark | Threshold | Overlap | Within |
|---|---|---|---|
| MSSBench chat | 4.1 | 5.5 | 3.4 |
| （第二列） | 4.6 | 1.5 | 3.7 |
| （第三列） | 1.7 | 6.2 | 5.7 |
| （第四列） | 3.9 | 2.5 | 3.7 |
| （第五列） | no pairs | no pairs | no pairs |
| （第六列） | 5.3 | 5.5 | 7.3 |

**读法**：只有第一、二列是"阈值占主导"；第三、六列是"重叠和顺序占主导"。**同一个 gap，在不同 benchmark 上有完全不同的病因。**

### recentering 的失效边界

| 条件 | 结果 |
|---|---|
| AUROC > 0.70 | 回收率接近阈值项上限 |
| AUROC < 0.70 | **五个模型里三个变差**（校准反而伤害） |
| Avg-2（两次采样取平均） | chat AUROC 提到 **0.898**，但**只缩阈值项**，重叠项和对内顺序项不动 |

这条对我们是硬约束：**免标注校准只在"排序本来就不错"的时候有效。排序不行的时候，校准是负收益。**

### 十四个模型的普遍现象

- **R − A 在十四个模型上全部为正**（在 label-swap null 之上）
- **十四个里有大多数"排序比打标好"，超出的部分多于 AUROC 所能预测的**
- 一个共享阈值能修 **1/3 到 1/2** 的超额
- 剩下的主要是**重叠**：最好的共享阈值之后还剩 **6.9 点**（两个最好的 chat 排序器）

## 四、实验与结果

### Benchmark Card 摘要

| 项 | MSSBench chat | 其余五个 |
|---|---|---|
| File-only rule | **size rule 82.3%** | size rule ≤ 51.3% |
| Metadata classifier | AUROC **0.879** | 0.484 / 53.2% / 0.477 |
| Request-only | AUROC 0.601 | 0.578；0.503 |
| 泄漏判定 | **是，size rule 82.3%** | 否 |
| Threshold/Overlap/Within | 4.1 / 5.5 / 3.4 | 见上表 |

### 主结果

| 项 | 数 |
|---|---|
| 被测模型数 | **14 个开源 MLLM** |
| R − A 为正的模型数 | **14 / 14** |
| 一个共享阈值能修的超额比例 | **1/3 – 1/2** |
| 最优共享阈值后剩余（两个最好的 chat 排序器） | **6.9 点**（全部是重叠） |
| Avg-2 后的 chat AUROC | **0.898** |
| 纯文本分最高 | AUROC **0.914**（Molmo2-O-7B） |
| 文件规则上限 | 最多 **58.2%**（除 MSSBench 外的文件规则） |
| recenter 在 VSCBench 上改善的模型数 | **13 / 14** |

### 一条容易被忽略的诚实说明

论文明确处理了"成对结构可能让数据变简单"的问题：在 150 对**请求完全相同**的 embodied 对比上，各模型的 AUROC 仍然保持，说明**成对设计没有人为抬高排序能力**。这是这篇少数主动做的鲁棒性检查。

## 五、局限性

1. **只测"情境安全"这一类 benchmark**（场景里有没有危险），不是内容安全（NSFW / 违规内容）。**这两类的分数结构不同**：情境安全的风险在"场景里"，内容安全的风险在"用户要什么"。所以三项分解的比例不能直接搬。
2. **分解依赖成对结构**（安全/不安全场景 + 相同请求）。我们的评测集没有这种结构，**要自己构造**。
3. **十四个模型全是开源的**，没有闭源模型；Wiqonn 是两人公司，没有工业部署验证。
4. **"label-swap null"是个构造**，它的合理性依赖"交换标签后分数分布不变"这个假设，论文没有对这个假设做敏感性分析。
5. **recentering 的具体做法在不同 benchmark 上不完全统一**（批次均值 / 同情境未标注场景），回收率的可比性有限。
6. **三个 part 的加和等于 R − A 是定义上的恒等式**，所以"分解正确"不构成证据；真正的证据是**各部分的比例在不同 benchmark 上不同**，以及 **recenter 只动阈值项不动其他两项**。

## 六、复现指南

### 环境
- 只需要**分数**：每条样本的 label score（连续）+ 模型直接回答（对/错）
- 需要**成对结构**：同一请求下的一个安全场景 + 一个不安全场景

### 最小复现路径（对我们最省力）
1. **先算两个数**：把现有评测集的 **AUROC（R）** 和 **balanced accuracy（A）** 都算出来。如果 R 明显高于 A，说明"会排不会判"，差额就是可优化空间。
2. **找最优共享阈值 $A^*$**：扫一遍阈值取最优 balanced accuracy。得到阈值项 $A^* - A$。
3. **算重叠项** $\mathrm{AUROC} - A^*$ 与**对内顺序项** $R - \mathrm{AUROC}$。
4. **按比例决定投哪**：
   - 阈值项占大头 → **做 operating point 校准**（每类目单独扫阈值）
   - 重叠项占大头 → **阈值无用，必须改分数**（补数据 / 改 loss / 加特征）
   - 对内顺序项占大头 → **绝对定标坏了但成对判断还在**，可以用成对比较代替绝对阈值

### 关键超参
- 零假设：label-swap null（交换标签重算 R 的期望）
- 置信区间：group bootstrap（95%）
- recentering：批次分数均值 / 同情境未标注场景均值

## 附：怎么用这一篇结束"调阈值 / 补数据 / 改标签"的三选一

我们当前的基线与三轮纠结：

| 指标 | 值 |
|---|---|
| 误杀率 | **5.2%** |
| 漏过率 | **3.42%** |
| 一级一致率 | **77.64%** |

**77.64% 是一个"打标"指标（对应本文的 A）。** 我们从来没算过对应的 **AUROC（R）**。这就是缺的那一格。

一旦补上，就有三条互斥的行动路线，而且**不需要再争论**：

| 若 | 则 | 依据 |
|---|---|---|
| R 明显高于 77.64%，且**阈值项**占大头 | 做**分业务粒度的 operating point 校准**：按一级/二级/叶子类目各自扫阈值，在误杀 ≤5.2% 的约束下最小化漏过 | 本文：一个共享阈值能修 1/3–1/2 的超额 |
| 阈值项很小、**重叠项**占大头 | **调阈值到此为止**，转去做数据/loss/特征 | 本文：最优共享阈值后剩余 6.9 点全是重叠，阈值救不了 |
| **对内顺序项**占大头 | 放弃绝对阈值，改用**成对比较**（同 prompt 的两个变体谁更危险） | 本文：within 项是成对能力，与定标无关 |

**并且必须先测一条前置条件**：本文显示 recentering 在 **AUROC < 0.70 时五个模型里三个变差**。所以"先用免标注校准救一下"这个念头，只有在 R > 0.70 时才成立。

**同时要抄的一条审计纪律**：本文发现一个 benchmark 的图片尺寸单独就能到 82.3%。我们要自查的对应项是——**我们的评测集里，有没有哪个"跟标签无关的元信息"能单独把标签判出来**（prompt 长度？样本来源？标注批次？回流渠道？）。如果有，那张表上的所有版本对比都要重算。
